# 三端工作边界与接口决策

更新日期：2026-09-30。用户已回复“按照你的思路来”，接受 PCB 采集 IMU、Linux 管理 4G/NTRIP 的方案方向。下文保留备选比较作为设计依据；具体板卡引脚、通信速率和器件适配仍需验证。框架设计见 [C++ 框架设计](04_CPP框架设计.md)，尚未开始代码实现。

## 1. 已确认的边界

硬件进一步明确为：两只多星多频蘑菇头天线、指定工控机 16GB 基础套餐、海康工业相机、三星 SSD＋希捷 HDD、合宙 Cat4、Surface Windows 上位机。详细确认程度见 [硬件选型确认表](05_硬件选型确认表.md)。

| 端 | 已确认职责 | 范围说明 |
|---|---|---|
| 自研 PCB | 实时硬件、电源管理、时间同步、IMU 采集及时间戳 | 沿用 ADIS16477 系列作为设计假设；具体芯片及通信接口尚未冻结 |
| Linux 工控机 | 雷达、相机等设备接入、数据采集与存储 | 不承担在线轨迹解算、在线 AI 识别或 AI 告警；可以报告采集、磁盘、电源、同步及通信故障 |
| Windows 上位机 | 深度参数设置、局域网下载、回放、标定、轨迹解算、点云生成、AI 识别、跨次变化分析 | 算法集中在此端；设备操作和离线处理分模块组织 |
| UMD982 | 双天线定位、定向与授时 | 用户最终明确型号及双天线需求；实际板卡、配套与报价仍需确认 |
| 4G | 获取 RTCM 差分数据 | 数据与 NTRIP 接 Linux，PCB 管供电复位；不作为原始数据导出通道 |

“Linux 不在线解算”指不在工控机运行项目的轨迹融合/SLAM 等算法；UMD982 自身使用差分数据输出定位结果，与此边界兼容。

## 2. 三端模块提纲

### 2.1 PCB

- 分路电源控制与状态监测，硬件异常保护。
- 外电掉电检测、通知 Linux 保存关机、接收应答及最终断电策略。
- GNSS PPS 捕获、定时器时间基准、相机硬件触发及同步状态。
- 按键、指示、看门狗、配置读写、板级诊断及固件升级接口。
- IMU：SPI/DRDY 采集、时间戳、序号、有界缓存及上行数据协议。
- 4G：仅供电和必要硬件复位；网络管理、NTRIP 和 RTCM 转发归 Linux。

### 2.2 Linux

- 设备管理：发现、配置、启停、健康状态与断线重连。
- 采集管理：雷达、四路相机、GNSS、IMU 数据接收以及 PCB 状态。
- 任务管理：任务编号、元数据、设备身份、标定引用及配置快照。
- 存储管理：原始数据、分段、索引、校验、磁盘水位及中断恢复。
- 参数服务：统一处理 Windows 请求，将操作转发给实际设备，读回结果。
- 局域网服务：任务浏览、下载、续传和校验；下载不应挤占采集所需带宽和磁盘资源。
- 差分服务：按最终硬件接入方案运行或监测 NTRIP/RTCM 链路。
- 诊断：记录丢帧、丢样、时钟失锁、差分中断、供电异常和设备重启。

### 2.3 Windows

- 设备连接及详细参数设置；采集启停、状态查看和配置导入导出。
- 局域网任务下载、断点续传、完整性校验及本地项目管理。
- 多传感器同步回放、时间轴、图像/点云/轨迹与质量状态展示。
- 内外参、杆臂、时间偏差、坐标系和标定版本管理。
- 轨迹解算、点云去畸变和点云生成。
- 离线 AI 推理、目标与事件复核、跨次巡检对齐及变化分析。
- 作业队列、批处理、取消和恢复、成果导出与报告。

Windows 上位机与计算核心建议分离；Qt 负责交互，C++ 库负责数据和算法。PCB 可采用 C/C++ 及厂商底层库。Linux 与 Windows 共享协议和数据定义，但不要求三端链接同一个二进制库。具体标准、依赖和工程目录在方案确认后制定。

## 3. IMU 接入：决定因素是采样时刻与可靠读出

要分别评估三件事：传感器何时产生样本、系统何时读走样本、Linux 何时收到数据。后两者存在延迟并不自动意味着采样时刻错误，但如果没有可靠时间戳或缓冲，可能丢失时序信息或覆盖未读样本。

若沿用原方案 ADIS16477，厂商资料明确提供 SPI、数据就绪指示和外部同步模式，可围绕这些接口设计采集。不能把软件收到数据的时刻直接视为物理测量时刻。[ADI 产品资料](https://www.analog.com/en/products/adis16477.html)

| 方案 | 优势 | 需要解决的问题 | 适用条件 |
|---|---|---|---|
| IMU → PCB → Linux | 可将 DRDY、PPS、相机触发放在同一硬件计时域；Linux 忙时由 PCB 缓冲 | 固件采集、缓存容量、上行带宽、溢出和重启处理；不能假设 MCU 天然不会丢样 | SPI 原始 IMU，需自行建立准确时间关系 |
| IMU → Linux | 链路短，驱动维护集中；可利用成熟内核驱动 | 核对载板 SPI/DRDY、驱动时戳位置、读取期限、硬件缓冲及最坏负载 | 平台提供可验证的采集机制，或 IMU 成品自带可靠时戳与缓存 |

PREEMPT_RT 调整中断和调度行为，可改善 Linux 的实时处理机制；是否满足本设备要求仍需在目标载板、驱动、存储和相机负载下测量。不能只通过开启实时内核就宣称同步满足指标。[Linux 官方说明](https://cdn.kernel.org/doc/html/latest/core-api/real-time/differences.html)

**已接受的方案方向：** 以 SPI 型 ADIS16477 为设计假设，优先验证 PCB 采集方案；Linux 负责接收和保存带源时间戳的数据。保留成品 IMU 直连 Linux 的接口可能，不同时实现两套生产链路。

### 3.1 建议验证项目

1. DRDY 硬件捕获、SPI 读取时长及截止时间；验证中断、DMA 和任务优先级。
2. PPS 与连续计数器建立映射，并结合绝对时间报文确定秒号；PPS 单独不含日期。
3. 根据传感器滤波/同步模式核查 DRDY 时刻与有效测量时刻的偏移。
4. 每帧保留原始计数、序号、设备/启动标识、同步质量和校验信息。
5. 按“样本率×每样本字节数×允许上行阻塞时间”核算缓存，并计入协议开销和余量。
6. 用四路相机、雷达、磁盘写入和局域网下载并发压测；检查丢样、最大延迟和缓冲溢出。
7. 测试 PPS 丢失、重获、计数回绕和 PCB 重启，避免生成看似正常的错误时间戳。

## 4. 4G 接入：网络通道与实时采样分开考虑

常见逻辑链路为：4G 网络 → NTRIP 客户端 → 差分服务 → RTCM 数据 → GNSS 接收机。4G 提供网络；NTRIP 客户端负责账号、挂载点、会话和转发。BKG 提供 NTRIP 及其客户端资料。[BKG NTRIP](https://igs.bkg.bund.de/ntrip/)

RTCM 的具体消息类型必须与 UMD982 及所用差分服务匹配，不能只检查“是 RTCM”。此前检索的其他型号手册不再作为本型号依据；后续应以 UMD982 对应硬件及固件版本的官方资料核验 PPS、端口配置、电平和双天线输出消息。

| 方案 | 逻辑链路 | 优势 | 代价与适用条件 |
|---|---|---|---|
| 4G 接 Linux | 4G → Linux NTRIP → UMD982 | 网络管理、配置、日志和 Windows 远程设置集中；减少 PCB 网络任务 | Linux 停机时差分会话停止；需驱动支持、重连和模组复位控制 |
| 4G 接 PCB | 4G → MCU NTRIP/模组内置客户端 → UMD982 | 可独立于工控机维持差分链路 | MCU 承担模组、网络、会话及恢复工作；须与采样任务隔离；适合明确要求 Linux 停机仍保持 RTK 的场景 |

**已接受的方案方向：** 4G 数据与网络控制接 Linux，PCB 管理模组供电和必要的硬件复位。这样供电归 PCB、网络业务归 Linux；模组物理安装在 PCB 上也不改变软件职责。

RTCM 链路要关注消息新鲜度、连续性和恢复时间；蜂窝网络延迟不会因为接入 MCU 就消失。监控收到字节的时间、有效消息状态、接收机差分龄期和定位状态，避免重连后向接收机灌入过期积压数据。

建议 UMD982 数据口归 Linux 管理，PPS 分配到 PCB 同步电路；绝对时间报文可直达 PCB 或经带秒号的协议转发，必须验证 PPS 边沿与秒号对应。若数据口改归 PCB，则 Linux 的配置/差分数据需要经 PCB 转发，增加的吞吐和故障路径另行评估。

## 5. Windows 深度参数设置的边界

Windows → Linux 统一参数服务 → 传感器 / PCB / NTRIP 服务。

| 参数类别 | 示例 | 处理原则 |
|---|---|---|
| 相机 | 曝光、增益、帧率、分辨率、触发方式 | 设备能力查询；带宽和触发关系联合校验 |
| 雷达 | 支持的扫描、回波、网络及同步设置 | 按设备支持范围开放，修改后读回 |
| IMU / 同步 | 采样、滤波、安装轴定义、触发频率 | 明确需停采或重启的参数，防止单端修改破坏时间关系 |
| UMD982 | 输出消息、频率、端口、差分配置及双天线定向相关参数 | 单一配置入口，避免多进程同时写同一串口；保存航向及其质量状态 |
| 4G / 差分 | APN、差分服务地址、端口、账号、挂载点 | 配置校验；密码不写普通日志或任务快照；按服务要求提供 GGA |
| 存储 | 保存路径、分段、保留策略与任务信息 | 检查空间和写入状态，避免采集中任意变更 |
| 电源 | 允许配置的延时、状态阈值 | PCB 保留硬件保护边界，远程参数不能绕过保护 |

参数应有当前值、允许范围、修改权限、生效时机、版本、读回和失败反馈。标明“立即生效 / 停采后生效 / 重启后生效”。每次采集保留不含凭据的配置快照，使后处理知道当时实际使用的参数。

## 6. 离线解算的数据前置条件

Windows 算法范围已经确认，但具体解算方法未定：

- 若使用接收机输出位置＋IMU＋点云做融合，应保存定位解、质量指标、IMU 原始数据、逐点/逐帧时间和标定。
- 若需要 GNSS 观测值级后处理，应验证 UMD982 所购版本的原始观测与星历输出能力，并准备对应的基准站/差分数据来源。
- 只保存 NMEA 位置或收到的 RTCM 字节，不自动构成完整的 GNSS 后处理输入。
- AI 与跨次变化分析需要保留可复用图像、点云、轨迹、坐标参考、标定版本和历史基准。

因此采集格式要先覆盖确定的后处理输入，再讨论文件大小优化。

## 7. 对原规划的影响

- 原 Jetson Orin NX 和 TensorRT 边缘推理方案不再自动成为工控机选型前提；现有硬件可继续使用，是否换型另行评估。
- Linux 按接口、数据吞吐、稳定性、存储、功耗和环境条件选型；Windows 按离线解算、点云和 AI 负载确定配置。
- 原 30ms 单帧推理、500ms 实时 AI 告警指标需从 Linux 验收中移除；Windows 应另定处理耗时和分析准确率。
- 原 Windows 岗位现在承担更完整的算法链路，原人工分工和工作量需要调整。

## 8. 决策状态与后续验证

1. 已接受“PCB 采集＋Linux 存储”；暂沿用 ADIS16477 系列，不据此直接采购。
2. 已接受“4G 接 Linux、PCB 管供电复位、UMD982 数据归 Linux、PPS 归 PCB”。
3. 轨迹解算先定义扩展接口并保存原始数据；GNSS 观测值级后处理需要另行核对接收机输出和基准数据，不声称首版已实现。

已确认的是功能分工和连接方向；电气原理图、时序精度及带宽仍以具体硬件验证为准。
