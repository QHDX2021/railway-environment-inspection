# C++ 框架设计

日期：2026-09-30。状态：书面设计待审阅，三端工作边界已确认。

最新硬件依据见 [硬件选型确认表](05_硬件选型确认表.md)。工控机为指定商品的 16GB 基础套餐，相机为海康工业相机，4G 为合宙 Cat4，Windows 终端为 Surface。具体型号/主机架构未核实时，不固定厂商 SDK、网口数量或 GPU 后端。Surface 承担完整后处理职责；Qt 与计算分离，采用后台任务、进度、取消和分块读取，界面考虑触控。AI 后端不预设 CUDA/TensorRT 依赖，处理速度在目标 Surface 上实测。

## 1. 目标与首版范围

截图补充：工控机为 Orin NX 系列 ARM64 平台，16GB；商品同时列出普通/SUPER 版本，具体 SKU 尚未核实。Linux 设备 SDK 与依赖按 ARM64 检查，JetPack/系统及编译工具链版本按实际镜像固定。截图的模组能力表不能直接替代载板接口清单；端口和存储扩展仍按 [截图核对](06_工控机截图参数核对.md) 验证。Linux 采集存储的业务边界不因 GPU 算力变化而调整。

建立主要使用 C++ 的三端工程框架，使后续硬件、采集、上位机和算法能够按明确接口分别开发。工程放在 `prj/framework/`，原项目梳理文档继续保留。

首版交付可编译、可运行的模拟采集闭环：模拟 PCB/传感器 → 采集程序 → 分段记录 → 离线回放；同时建立设备参数管理、差分转发边界及 Windows 后处理接口。模拟数据显式标记为模拟，不用模拟运行冒充硬件精度验证。

完整产品仍包含真实设备接入、局域网下载、Qt 参数界面、标定、轨迹解算、点云生成、AI 和跨次变化分析。首版框架为这些功能提供接口和集成位置；未接入的算法返回 `NotSupported`，不返回空的“成功”结果。

## 2. 三端职责与硬件连接

```text
                        自研 PCB
IMU ──SPI/DRDY────────→ 采集、计时、缓存 ───→ Linux
UMD982 PPS ──────────→ 时间基准/触发 ───────→ 相机
                        电源/状态/复位
                              ↕ 控制、状态、关机握手
雷达、相机 ───────────────→ Linux 采集和存储
UMD982 数据口 ←──────────→ Linux GNSS 服务
4G 网络 ──→ Linux NTRIP ──→ UMD982 RTCM 输入
                              ↕ 局域网
                    Windows 参数设置、下载
                              ↓
                    回放、标定、轨迹、点云
                              ↓
                        AI、跨次变化分析
```

- PCB 不承载 NTRIP 和图像/点云算法。IMU 型号暂按 ADIS16477 系列设计。
- Linux 不在线解算或运行 AI；保留设备故障与质量状态报告。
- Windows 是用户操作入口；远程设置通过 Linux 唯一设备管理入口执行。
- 定位模块明确为 UMD982，采用双天线方案。定位输出、双天线航向及质量状态、原始数据和差分输入由一个 Linux 服务统一管理，防止串口多写冲突。
- 配置与标定记录两根天线的主从身份、基线方向、相对车体安装关系及杆臂；Windows 解算使用相应版本，避免直接把天线基线航向视为车体航向。
- PCB 上行先定义与物理链路无关的帧协议；最终 UART/USB/以太网选择通过带宽、线长和板卡资源验证后确定。

## 3. 工程组织与依赖方向

建议 C++17、CMake 和 CTest。核心首版采用标准库，避免模拟运行必须安装 ROS2、Qt 或厂商 SDK。Qt6 为 Windows 界面独立可选目标；具体版本在实现时按环境固定。ROS2 不作为三端公共协议或首版编译前提。

```text
prj/framework/

  README.md
  shared/
    types/                  数据、时间、状态、错误码
    protocol/               PCB 帧协议与消息编解码
    configuration/          参数描述、校验和配置版本
    recording/              记录格式、读取、索引与校验
  firmware/
    core/                   电源/采集/同步状态机
    hal/                    SPI、计时器、传输等抽象接口

  linux/

    devices/                PCB、雷达、相机、GNSS 适配接口
    corrections/            NTRIP 会话与 RTCM 转发边界
    storage/                任务目录、分段写入与容量策略
    control/                参数、状态和局域网服务边界

    application/            项目、下载、处理任务管理
```

首版只为实际交付的接口和组件创建文件；未实现目录在说明中列出，不批量生成无行为的空类。

依赖方向：应用/适配器 → 服务 → 公共类型与协议。公共层不依赖 Qt、ROS2、厂商驱动；固件仅使用适合 MCU 的类型、编解码和状态机，不能把主机文件系统、网络或堆分配组件带入中断路径。

## 4. 数据与时间模型

每条记录包含版本、消息类型、流编号、设备/启动标识、序号、源时刻、接收时刻、时间质量、负载长度和校验信息。

- 源时刻由设备时钟提供，保留原始计数器及计数频率；同步映射另存。
- 主机接收时刻使用单调时钟。绝对时间以明确时间尺度表示，不混用 UTC、GNSS 时间与本地时间。
- 时间质量取 `Unsynchronized / Locked / Holdover / Invalid`；失锁不能继续标为精确同步。
- PPS 捕获必须与秒号报文关联；相机触发编号与图像编号建立对应，触发时刻不能自动等同曝光中心。
- IMU 保留原始量和比例/单位信息，统一计算接口使用 rad/s、m/s²；安装轴定义进入配置。
- 雷达保留逐点时间或可恢复它的原始包，图像保留设备帧号和曝光相关元数据。

具体采样时刻偏移由传感器模式与标定确定，首版模拟仅验证时间字段正确传递。

## 5. PCB 协议与固件状态机

### 5.1 消息

第一版消息类别：能力查询、状态、参数读写、采集启停、IMU 数据、PPS/时间映射、触发事件、电源事件、关机握手、错误响应。升级消息预留类别，首版不提供实际刷写操作。

帧格式：固定同步标识、协议版本、类型、序号、长度、负载、CRC。整数逐字段按小端编码；不直接发送 C++ 结构体内存。最大负载作为协议常量；解析器拒绝超长和不支持版本，支持半包、粘包、坏帧后重新同步。

编解码支持调用方提供的缓冲区，以便 MCU 无动态分配使用。控制请求有请求编号、超时、应答和错误码；重发必须使用同一请求编号，设备端对改变状态的请求去重。

### 5.2 状态与边界

采集：`Idle → Starting → Recording → Stopping → Idle`；故障进入 `Fault`，保留原因并由显式恢复流程退出。

掉电：检测 → 停止新任务 → 通知 Linux → Linux 停采、刷写并应答 → 发起关机 → 按实际硬件关机完成信号/经验证延时断电。文件刷写应答不等于操作系统已完成关机；超时策略必须结合备用电源能力配置并测试。

中断处理仅完成捕获、必要读取/调度及入队；参数、日志、协议应答在任务上下文处理。上行拥塞和采样缓冲溢出明确统计，不能静默覆盖。

## 6. Linux 服务边界

| 接口 | 责任 |
|---|---|
| `IDevice` | 能力查询、状态、配置、启动停止 |
| `ISampleSource` | 输出带原始时刻的数据和采集错误 |
| `IPcbTransport` | PCB 字节链路，协议解析不绑具体串口库 |
| `IGnssSession` | 独占管理 GNSS 输入输出和配置，序列化差分写入 |
| `ICorrectionSource` | 提供 RTCM 数据、接收时间和连接状态 |
| `IRecordingWriter` | 记录、分段、结束、错误及已持久化状态 |
| `IControlService` | 任务控制、参数读写、状态与下载目录 |

采用有界队列；容量、占用和丢弃计数可观测。关键原始采集队列满时显式标记任务数据不完整并按策略停采，状态预览等可丢弃数据使用独立队列。停止顺序为停源、排空、结束记录，不允许后台线程访问已析构资源。

NTRIP 服务由 Linux 管理，负责账号、挂载点、按服务要求发送 GGA、退避重连和错误记录。4G 拨号由独立平台适配层处理。GNSS 写入通路优先级和超时有界，重连丢弃过期差分积压。RTCM 字节到达不等于接收机已接受有效差分，应同时观察定位质量和差分龄期。

首版仅以模拟差分源验证转发接口及错误传播，不声明已有实网 NTRIP 兼容性。

## 7. 深度参数配置和局域网接口

参数描述包含名称、类型、范围、单位、默认值、只读标志、生效时机和设备能力限制。写入过程为校验、执行、读回、更新配置版本；读回失败不得报告成功。多设备部分应用失败要返回逐项结果，不伪装成跨设备原子事务。

首版模拟至少覆盖曝光、触发频率和采集开关的状态限制。采集中不能直接修改必须停采的参数。保存配置快照时过滤凭据。

产品局域网接口采用版本化 HTTP/JSON 控制和文件下载接口，后续真实网络适配按该边界接入：

- 查询设备能力/状态，读写参数并携带预期配置版本。
- 创建任务、启停任务、列举任务及文件清单。
- 文件按任务 ID/文件 ID 寻址，不接受客户端任意文件路径。
- 下载支持范围请求、文件长度和摘要校验；已封闭分段可下载，当前写入分段不发布。
- 单一控制所有者或等价锁机制防止多个 Windows 客户端同时改配置；请求具备认证，凭据不进入日志。

首版工程测试通过进程内控制服务模拟这些操作；真实 HTTP 服务、认证、续传和远程客户端是后续集成阶段，不能将接口定义算作完成联机下载。

## 8. 记录与回放

每个任务目录包含任务清单、设备与配置快照、分段数据、索引、时间映射、诊断计数和标定引用。首版任务清单使用简单的版本化 UTF-8 文本键值格式；设备原始负载封装在版本化二进制记录中，避免首版为了 JSON 增加依赖。后续网络 JSON 与磁盘格式互相转换。

二进制文件带版本；逐条记录有长度边界和校验，不使用平台相关的结构体布局。读取器能够识别尾部截断和坏校验；恢复模式只返回完整记录，明确报告损坏和任务未正常关闭，默认严格模式返回失败。

索引损坏时允许重扫有效记录重建。任务清单先写临时文件再完成替换；不能把原子重命名等同断电持久化保证，真实 Linux 适配需验证刷盘和供电切换。

GNSS 原始字节、消息格式、固件版本和输出配置应保留。观测值级后处理需要的观测、星历和基准数据尚未得到硬件验证，不能把 RTCM/NMEA 记录称为完整后处理输入。

## 9. Windows 后处理接口

| 接口 | 输入 | 输出 |
|---|---|---|
| `ICalibrationProcessor` | 选定样本、现有参数、标定任务配置 | 参数版本、残差与适用设备 |
| `ITrajectorySolver` | IMU、GNSS、可选点云、标定 | 带时间和质量的轨迹 |
| `IPointCloudBuilder` | 雷达原始数据、轨迹、标定 | 带坐标系和来源的点云成果 |
| `IAiAnalyzer` | 图像/点云、模型与类别配置 | 检测结果、置信度和证据引用 |
| `IChangeAnalyzer` | 两次巡检成果、坐标系及配准参数 | 变化区域、指标与复核证据 |

处理任务统一具有输入校验、进度、取消、错误、结果清单和版本信息；输入缺失即明确失败。结果引用原始任务和配置，不覆盖原始数据。每个算法模块可以独立替换，Qt 界面不承担算法实现。

首版提供上述接口和未安装算法的明确提示。回放读取、时间筛选与统计是真实实现；复杂算法与三维 GUI 不是首版框架内假定已经完成的部分。
