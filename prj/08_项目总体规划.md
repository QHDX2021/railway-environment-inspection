# 车载式铁路周边环境巡检项目总体规划

**版本：** V1.0

**整理日期：** 2026-10-08

**规划状态：** 总体架构已确认，具体器件型号、接口参数和验收数值按冻结门禁逐项确认。

## 1. 项目目标

建设一套车载式铁路周边环境巡检系统，完成多传感器同步采集、原始数据可靠记录、局域网下载、离线处理和结果复核。系统最终应支持：

- 激光雷达、工业相机、IMU、UMD982 双天线 GNSS 的同步采集；
- 任务管理、原始数据记录、完整性校验、异常恢复和回放；
- Windows 端深度参数设置、标定、轨迹解算、点云生成；
- AI 目标识别、人工复核和跨次环境变化分析；
- 现场安装、连续运行、维护升级和验收交付。

项目按“先保证数据可靠，再开展算法处理”的顺序推进。Linux 工控机负责采集、存储和设备管理，Windows 上位机负责离线计算和分析。

## 2. 产品边界

### 2.1 自研 PCB

PCB 采用 STM32H750 方向设计，负责实时硬件和与采集时刻相关的功能：

- ADIS16477-3 的 SPI/DRDY 采集、源时间戳、序号和缓存；
- UMD982 PPS 捕获、秒号映射和统一时间基准；
- 相机硬件触发和触发编号；
- 分路供电、状态检测、看门狗、故障保护和必要的 4G 硬件复位；
- 外部掉电检测、通知 Linux 停采、关机握手和断电策略；
- 与 Linux 之间的版本化二进制协议。

PCB 不承担 NTRIP 会话、点云处理、轨迹解算和 AI 分析。

### 2.2 Linux 工控机

Linux 以 Jetson Orin NX 16GB ARM64 方案作为当前设计依据，具体 SKU、载板和系统版本通过实物资料冻结。Linux 负责：

- XT32、四路海康工业相机、PCB、UMD982 和合宙 Cat4 的设备接入；
- 采集任务启停、设备状态、断线重连和诊断；
- 多流数据接收、缓存、分段写入、校验和恢复；
- 4G 拨号、NTRIP 会话、RTCM 转发和差分状态监测；
- 参数读写、任务管理、日志和局域网控制/下载服务。

Linux 不运行项目的在线轨迹解算、在线 AI 识别和 AI 告警流程。设备故障、磁盘、同步和通信质量可以在 Linux 侧实时报告。

### 2.3 Windows 上位机

Windows 上位机采用 Surface 平板作为目标终端，具体型号和性能通过实测冻结。上位机负责：

- 设备连接和深度参数设置；
- 局域网任务浏览、下载、断点续传和完整性校验；
- 多传感器回放、时间轴和质量状态展示；
- 相机内参、雷达/IMU 外参、杆臂、时间偏差和坐标系管理；
- 轨迹解算、点云生成和结果导出；
- AI 识别、人工复核、跨次配准和变化分析；
- 批处理、进度、取消、失败恢复和报告生成。

Qt 负责交互界面，C++ 库负责数据访问、任务调度和算法接口，避免把算法逻辑写入界面事件处理。

## 3. 总体数据链路

```text
双天线蘑菇头天线 → UMD982 ──定位/航向/授时──→ Linux
                              └─ PPS ──→ 自研 PCB

ADIS16477-3 ──SPI/DRDY──→ PCB ──带源时间戳数据──→ Linux
PPS ──→ PCB ──→ 相机硬件触发

XT32 ────────────────┐
四路海康工业相机 ─────┼──→ Linux 采集和记录
合宙 Cat4 ─NTRIP/RTCM─┘

Linux ──局域网──→ Surface Windows
                    ├─参数配置和任务控制
                    ├─数据下载和回放
                    ├─标定、轨迹和点云
                    └─AI 与跨次变化分析
```

4G 的推荐职责为“Linux 运行网络和 NTRIP，PCB 管理供电和必要复位”。UMD982 数据口由 Linux 统一管理，PPS 进入 PCB 同步电路。最终电气连接、串口归属和恢复策略以接口验证结果为准。

## 4. 硬件冻结计划

### 4.1 当前硬件基线

| 部件 | 当前选择 | 仍需冻结的内容 |
|---|---|---|
| 激光雷达 | 禾赛 XT32 | 具体型号、供电、网络、同步和 SDK |
| IMU | ADIS16477-3，PCB 采集 | 量程、采样率、SPI/DRDY、电气连接和安装标定 |
| PCB | STM32H750 自研板 | 原理图、器件、引脚、接口、保护和测试点 |
| GNSS | UMD982，双天线 | 完整板卡、数据输出、PPS、RTCM、双天线配置 |
| 天线 | 多星多频蘑菇头天线 2 只 | 具体型号、频段、馈线、接头、基线和安装防护 |
| 工控机 | Jetson Orin NX 16GB 方案 | 普通/SUPER SKU、载板、JetPack、接口、供电和散热 |
| 相机 | 海康工业相机 4 台 | 具体型号、分辨率、帧率、接口、触发、镜头和 SDK |
| 存储 | 三星 SSD、希捷 HDD | 型号、接口、数量、转接、供电、固定和振动验证 |
| 4G | 合宙 Cat4 | 具体模块、Linux 接入方式、SIM、天线和峰值功耗 |
| 上位机 | Surface 平板 | CPU 架构、内存、磁盘、局域网接入和处理性能 |

### 4.2 硬件冻结门禁

硬件进入整机采购前必须取得以下证据：

1. 具体型号、版本、供电范围、接口和配套清单；
2. 设备带宽、存储写入、网络和供电预算；
3. Linux ARM64 驱动或 SDK 可用性；
4. PPS、硬件触发、时间戳和丢帧诊断能力；
5. 机械尺寸、安装方向、散热路径、线束和维护空间；
6. 单件台架测试记录和替代料规则。

商品宣传图只作为选型线索，不能替代载板手册、厂商数据手册和实测结果。

## 5. 软件总体结构

工程采用 C++17、CMake 和 CTest。公共层不依赖 Qt、ROS2 或厂商 SDK，真实设备通过适配器接入。

```text
prj/framework/
  shared/       公共类型、协议、参数、记录格式
  firmware/     MCU 状态机、HAL 和板级接口
  linux/        设备适配、采集、存储、差分、控制
  desktop/      Windows 回放、任务、处理接口和 Qt 适配
  adapters/     模拟设备和厂商适配边界
  apps/         采集演示、回放和诊断工具
  tests/        协议、状态、记录、采集和处理测试
  docs/         协议、格式、接入和验证文档
```

核心数据模型必须保留：设备编号、启动编号、序号、源时刻、主机接收时刻、时间质量、负载、配置版本和校验信息。同步失锁、缓存溢出、丢帧和任务未正常关闭必须显式记录。

## 6. 研发工作包

### W1 需求和接手

盘点现有样机、BOM、PCB、源码、配置、标定、供应商资料和历史问题，输出资产清单、缺口清单、需求规格和验收矩阵。

### W2 接口和关键器件验证

使用目标载板和样件验证 UMD982、IMU、相机、雷达、Cat4 的驱动、带宽、供电、时间同步和异常恢复，冻结接口控制文档。

### W3 PCB 和固件

完成同步板原理图、PCB、板级测试、IMU 采集、PPS 映射、触发、电源状态、看门狗、关机握手和主机协议。

### W4 Linux 采集和存储

完成设备管理、多流采集、有界队列、记录分段、索引、磁盘水位、故障恢复、日志和 NTRIP/RTCM 服务。

### W5 局域网控制和下载

完成版本化 HTTP/JSON 接口、参数读写、任务管理、封闭文件下载、范围请求、断点续传、摘要校验和单一控制所有者。

### W6 Windows 工具链

完成参数设置、任务下载、回放、配置快照、标定管理、轨迹/点云处理接口、作业队列和结果导出。

### W7 算法和数据集

依次完成标定、轨迹、点云、AI 识别、跨次变化分析。每个算法保存输入任务、配置版本、模型版本和结果证据，独立提供可复现评价。

### W8 整机和交付

完成结构、电源、散热、装车、长时间运行、异常工况、现场试验、版本冻结、部署包、操作手册和维护资料。

## 8. 验收指标体系

具体数值由 G1 冻结，验收维度先固定为：

- **数据完整性：** 记录数量、序号连续性、CRC、断电恢复和损坏定位；
- **时间质量：** PPS/秒号关联、源时间戳、触发对应、失锁和恢复状态；
- **设备稳定性：** 连续运行、设备重连、网络中断、磁盘水位和线程退出；
- **空间成果：** 标定残差、轨迹质量、点云配准和坐标系一致性；
- **算法效果：** AI 分类/检测指标、变化分析有效率、误报漏报和人工复核闭环；
- **工程质量：** 温升、功耗、振动、防护、部署、升级和维护可操作性。

## 9. 当前基础和后续优先级

`prj/framework` 已完成 C++17/CMake 首版基础，包括公共协议、参数服务、状态机、模拟采集、记录回放、RTCM 转发边界、Windows 处理接口和自动测试。真实 PCB、厂商 SDK、Qt 界面、HTTP 服务、标定、轨迹、点云、AI 和跨次算法仍属于后续工作。

下一阶段按以下顺序执行：

1. 完成硬件接口冻结表和数据格式冻结；
2. 获取并核对 UMD982、工控机载板、相机、XT32、Cat4 的正式资料；
3. 搭建单件接口验证台，优先验证同步、带宽、供电和 ARM64 SDK；
4. 将模拟适配器替换为真实设备适配器，保持记录和回放接口不变；
5. 完成第一代连续采集样机，再进入 Windows 算法和整机联调。

## 10. 主要风险

| 风险 | 影响 | 控制措施 |
|---|---|---|
| 工控机 SKU/载板接口不明 | 相机、雷达和存储无法布置 | 采购前取得载板手册并做端口、带宽和供电核算 |
| 相机 ARM64 SDK 或触发能力不足 | 无法形成稳定四路采集 | 先买单路样机验证 SDK、触发、帧号和丢帧 |
| UMD982 输出能力与后处理需求不匹配 | 轨迹解算输入不足 | 核对观测值、定位、航向、PPS、RTCM 和原始数据输出 |
| 同步链路缺乏测量依据 | 点云和轨迹质量不可控 | 建立 PPS、DRDY、触发和主机接收的实测记录 |
| 存储吞吐或掉电保护不足 | 数据丢失 | 先做多流写入、磁盘满、掉电和恢复测试 |
| Surface 算力不足 | 后处理时间过长 | 使用真实任务做目标终端性能基准，保留批处理和分块机制 |
| 跨次变化数据不足 | AI/变化分析难以验收 | 早期建立路线、季节、天气和变化类型数据集 |

## 11. 规划结论

项目首先交付一条稳定、可回放、可追溯的数据链路，再逐步叠加标定、轨迹、点云、AI 和跨次变化分析。硬件型号和接口证据是进入真实驱动开发的门槛；公共 C++ 数据格式、协议和任务生命周期是三端并行开发的基础。
